## What was implemented

This is the first network traffic the project has ever produced. Before this branch
`AndroidManifest.xml` had no `INTERNET` permission, `data.remote` was a declared-but-uncalled
scaffold, and the home screen's weather card read a hardcoded `Parkville · 18°C`.

- **Provider.** Open-Meteo's `v1/forecast` current-conditions endpoint. Selected for the weather
  half of D-02 because it is HTTPS, free for non-commercial use, and needs no API key and no
  account — which removes the entire credential-handling problem rather than managing it, and lets
  a reviewer check the repository out and run it with no setup. Rejected alternative:
  OpenWeatherMap, which is the more common course choice but requires a registered key that would
  have to travel through `local.properties` and `BuildConfig`, and without which the feature would
  be dead for anyone else holding the repository.
- **Domain.** `WeatherCondition` (with `UNKNOWN` as a real category), `WeatherSnapshot` (Celsius
  fixed at the mapper boundary, observation time and fetch time carried separately, provenance),
  `WeatherAreaBucket` (0.05-degree grid), `WeatherFreshnessPolicy` / `WeatherFreshness` /
  `WeatherResult`, and the `WeatherRepository` contract with a typed
  `WeatherUnavailableException.Reason`.
- **Remote.** `WeatherApiService` / `WeatherDto` / `RemoteWeatherMapper` (WMO code table, unit
  check, offset-aware timestamp parsing, rejection of non-finite and implausible temperatures), and
  `RetrofitWeatherSource`, which is the only class in the weather path that touches a socket.
- **Local.** Schema version 4 adds `weather_cache`, keyed on the area key. `MIGRATION_3_4` is
  purely additive and `4.json` is exported and committed.
- **Repository.** `CachedWeatherRepository` implements cache-first, per-area request coalescing,
  stale-as-fallback and atomic replace. `AndroidConnectivityMonitor` implements the existing
  `ConnectivityMonitor` interface as a hint only — a real request failure is still handled when it
  says the device is online.
- **UI.** One `WeatherViewModel` serves both the nearby card and a new optional weather section on
  the exploration dashboard. It follows the coordinator's accepted samples and starts no location
  updates of its own. Weather is deliberately *not* folded into `NearbyUiState`: a weather outage
  must not be able to put the attraction list into an error state.

### NFR-04.3

`ApiClientFactory` previously used OkHttp's `HttpLoggingInterceptor` at `BASIC` in debug builds,
with a comment claiming that omitting headers meant no key could leak. That reasoning was wrong for
this app: `BASIC` logs the full request line including the query string, and the weather request
carries coordinates. It is replaced with an interceptor that logs method, host, path and status and
never the query, and the `logging-interceptor` dependency is removed so the level cannot be raised
back by accident.

### Three defects this found

1. **A malformed payload was reported as "offline".** `RetrofitWeatherSource` originally classified
   every `IOException` as `NO_NETWORK`. Gson signals an empty or non-JSON body by throwing
   `EOFException` and `MalformedJsonException`, both `IOException` subclasses, so a broken payload
   would have told the user to find a better signal for a problem no signal could fix. Caught by
   `RetrofitWeatherSourceTest`; those two are now handled ahead of the transport branch.
2. **The card kept saying "Reference area" after the user's own fix arrived.** Found on the
   emulator, not by a test. `onSample` set the label to live and then called `request(...)`, which
   returns early when the area key has not changed — and the first fix normally lands in the very
   cell the reference area covers, so nothing republished. The observation was right and the label
   was a lie. Now the state is re-published under the new label without refetching; regression test
   `aFixInTheSameCellAsTheReferenceAreaStillStopsSayingReferenceArea`.
3. **A screen opened mid-session started out claiming the reference area.** The exploration
   dashboard builds its own `WeatherViewModel` after the session is already running, and the
   coordinator replays its snapshots to a new observer but not its last sample — so the dashboard
   would show "reference area" over a live walk until the next fix. It now seeds from
   `coordinator.routeSnapshot().getLastSample()`; regression test
   `aScreenOpenedMidSessionStartsFromThePositionTheCoordinatorAlreadyHas`.

## Limitations and defects

- **REQ-19.3 is only half implemented.** Weather is displayed on discovery and on the exploration
  dashboard, but it is **not** copied into the session record. That was planned for this round and
  deliberately dropped: nothing reads session history yet — `ui.journey` still renders
  `InMemoryJourneyRepository` — so the columns would have been write-only. They belong in the
  schema change REQ-16 already needs.
- **REQ-20 is partially covered, not complete.** Freshness, cache-as-fallback, coalescing, typed
  failure reasons and atomic replace are implemented and tested for weather. Bounded retry/backoff
  (REQ-20.2) is not implemented — there is no automatic retry at all, only the user tapping the
  card — and none of this is applied to the attraction path, which has no remote source until
  REQ-18.
- **Emulator only.** No physical device, no API 26 and no API 31+ run, in common with every other
  requirement in the project.
- **The provider is trusted for correctness, not just for shape.** The mapper rejects implausible
  and malformed readings, but nothing verifies that Open-Meteo's answer for a cell matches the
  actual weather at that location. Attribution is recorded in `WeatherApiService`'s Javadoc and is
  not yet displayed in the UI; REQ-18 will need a visible attribution surface, and weather should
  join it.
- **No throttle above the freshness rule.** The ViewModel asks the repository on every accepted
  sample and relies on the area check and the cache to make that free. That is correct but means a
  cache read per fix; if it ever shows up in the NFR-05 trials, the cheap fix is a time-based guard
  in the ViewModel.
