## What was implemented

Saving became real. Before this branch the Save control on the detail screen showed a Toast and
wrote nothing, and `SavedFragment` rendered `NearbyAttractionsViewModel`, so the "saved list" was
the nearby list under a different title.

- Schema version 3 adds `saved_attractions`, keyed on `attraction_id`, carrying a copy of the
  attraction's name, category, description, indoor flag and coordinates plus `saved_at_millis`.
  `MIGRATION_2_3` is purely additive and `3.json` is exported and committed.
- The table deliberately declares **no** foreign key onto `attractions`, unlike `visits` which
  cascades from its session. A cascade there would turn every cache refresh or eviction into a
  silent unsave, which is exactly what REQ-17.3 forbids.
- `SavedAttractionRepository` (domain) and `RoomSavedAttractionRepository` (data) follow the
  existing store pattern: I/O executor for work, main executor for callbacks. The repository is
  process-scoped in `AppContainer` and publishes the set of saved identifiers to observers, which
  is how the detail screen, the nearby list and the saved list stay in agreement without knowing
  about each other.
- Save is idempotent (`OnConflictStrategy.IGNORE`, so a repeat save keeps the original
  `saved_at_millis` and does not reorder the list); unsave of an unsaved place reports `false`
  rather than an error.
- Rapid toggles are serialised per attraction in the ViewModels: a second tap while a write for
  that attraction is outstanding is ignored, and the screen keeps showing the last state the store
  confirmed. A failed write reverts to that state and reports the failure once.
- `PrivacyDataFragment`'s "Clear saved places" is no longer a prototype dialog; it clears the table
  through `PrivacyDataViewModel`. "Clear journey history" remains a prototype, pending REQ-16.
- `loadSavedIds` exists on the contract for REQ-21 to consume; no ranking uses it yet.

## Limitations and defects

- **AT-17B is only half covered.** "Clearing the attraction cache does not unsave anything" is
  proved by `SavedAttractionDaoTest`, but there is no remote cache to refresh or evict yet — that
  arrives with REQ-18 — so the refresh half of the case cannot be executed. It must be re-run once
  a real content service is wired in.
- **Emulator only.** No physical device has run any of this, in common with every other
  requirement in the project. The physical half of AT-17A/AT-17B stays NOT_RUN.
- **Opening a saved place's detail screen still reads the attraction cache.** The saved record is
  self-contained, but `AttractionDetailFragment` loads by identifier through
  `AttractionRepository`, so a saved place that the cache no longer holds would show the detail
  error state. Nothing can currently evict a seeded row, so this is not reachable today; it becomes
  reachable with REQ-18 and should be resolved then, either by falling back to the saved copy or by
  keeping saved places pinned in the cache.
- **The Saved screen's search control is still non-functional.** It was a prototype affordance
  before this branch and is unchanged.
- **Failure feedback uses `Toast`,** matching the rest of the codebase rather than the Snackbar the
  plan named.
- **API 26 and 31 coverage is outstanding,** the same gap recorded for REQ-14/REQ-15.
