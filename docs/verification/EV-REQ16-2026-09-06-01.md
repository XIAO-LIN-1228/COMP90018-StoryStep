## What was implemented

History stopped being a prototype. Before this branch the journey list, detail and summary screens
all read `InMemoryJourneyRepository`'s three hard-coded rows, `JourneyDetailFragment` was 39 lines
with no ViewModel and no session id, and the privacy screen's "Clear journey history" only showed a
toast. The session tables underneath had been recording real data since REQ-15, and REQ-13 had been
writing real visits into them since the arrival round — there was simply no reader.

- **A separate `HistoryRepository` contract** (`domain.repository`) over the same session DAOs,
  rather than more methods on `SessionStore`. The store is the coordinator's write path and every
  invariant it documents is about a walk happening now; history is a read-and-delete path with
  different callers and a cross-screen observer. `Journey`, `JourneyRepository`,
  `InMemoryJourneyRepository`, `JourneyNotFoundException` and their test are deleted.
- **Schema version 5** adds nine columns to `sessions`: the weather observed during the walk, the
  movement totals it accumulated, and a sticky `interrupted` flag. `MIGRATION_4_5` is additive and
  back-fills `interrupted` for rows still carrying `pause_reason = 'PROCESS_INTERRUPTED'` — the one
  fact version 4 recorded that can honestly be carried forward. A composite index on
  `(finished, end_wall_clock_millis)` serves the list query.
- **REQ-19.3's remaining half.** The coordinator gained a nullable `WeatherRepository` and captures
  on the session's **first accepted fix** — not at `create()`, where the only coordinate available
  is the demonstration reference origin, which would have written some other area's weather into the
  user's own history. One retry at Stop covers a walk that never managed a capture. The whole path
  is fire-and-forget: its callbacks touch no session state, no durability flag and no observer.
- **A segmented route sketch** (`RouteSketchView`), not `StoryMapView`. That view draws an invented
  street grid, and a real trace on fake roads is exactly the turn-by-turn impression REQ-16.2
  forbids. One `Path` per recorded span, with no code path that calls `lineTo` across a boundary.
  The projection maths lives in `domain.geo.RouteProjection` / `RouteSegments`, unit-tested.
- **Deletion** per session and clear-all, both confirmed, both restricted to finished sessions.
  Route points and visits cascade through their existing foreign keys; `saved_attractions` has no
  foreign key onto any of this and is structurally untouchable from here.

## Deliberate scope decisions

- **Clear-all removes finished sessions only.** A walk in progress, or one restored as paused, is
  not history; wiping it from a "clear history" control would silently discard something the user is
  still doing. That restriction is the "explicit scope" REQ-16.3 asks for and is stated in the
  confirmation dialog.
- **Two decorative controls were deleted rather than wired.** The journeys screen's "All" / "This
  month" chips filtered nothing and REQ-16 defines no filter scope, and the list row's map thumbnail
  could only ever have been invented — the list query deliberately does not load route points.
- **`StoryViewModel.load` now takes an optional session id.** It previously derived the session from
  the coordinator, which from a history screen is either null (falling back to the *current cached*
  story rather than the walk's preserved copy) or, worse, a different running session's id.
  Reopening still inserts nothing: `markVisitRead` is an `UPDATE … WHERE` that returns 0 for an
  unknown pair.

REQ-16.4's cases are covered by `RoomHistoryRepositoryTest`: empty history, 200 synthetic sessions,
ordering including a same-millisecond tie, an invalid session id, an unfinished session excluded and
undeletable, the deletion cascade, no orphan rows, and observer notifications that fire once per
real change and not for a no-op.

`SessionHistoryDaoTest` is the one that matters for deletion, and it is instrumented rather than
JVM: the JVM tests wire the cascade by hand through `FakeSessionDao.cascadeListener`, which can only
show the repository behaves correctly *given* a cascading store. Only real SQLite shows the cascade
runs at all. It does, and no orphan route point or visit survives either delete.

**AT-16A and AT-16B are NOT_RUN.** Both are manual acceptance cases requiring a walkthrough — two
sessions with visits and multiple segments, airplane mode, force-stop, relaunch, then cancel a
delete, confirm one, clear all, relaunch — and neither has been performed. The automated suite
covers the storage and state rules those cases exercise, but not the user-facing walkthrough.

## Outstanding

- AT-16A / AT-16B manual walkthroughs, on an emulator and then on a physical device.
- No physical device has ever run this project's instrumented tests, and no API level other than 36
  has been exercised. Every physical acceptance case for REQ-16 is therefore outstanding regardless
  of what the suite above reports.
- `interrupted` records only "was ever paused by a process interruption", per `PauseReason`'s own
  javadoc. If the team wants `PERMISSION_LOST` / `PROVIDER_LOST` labelled as well, the column should
  become a nullable `interrupted_reason TEXT` — and that decision has to be made before version 5
  ships, because changing it afterwards is another migration.
- A walk that never gets a fix, or one in a poor-network area, records no weather. That is the
  honest outcome under REQ-19.4, but it means AT-16A cannot assert a weather line is always present.
- `JourneySummaryFragment`'s own body is still prototype content; only the journey id it passes to
  the detail screen is real.
